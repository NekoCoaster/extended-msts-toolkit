# Physical-object enumeration beyond train chains

The manager's list at `[[0x7bdecc]+0x18]` provides an independent physical-object enumeration path. The existing train list is at manager+0x20. Each circular-list node has next/previous pointers and an object-table index at +8; resolve the object as `[[0x828108]+index*8]`. This is not a sweep of every allocated object-table entry.

Native lookup `006347ef` searches this +0x18 list for object+0x50 equal to a requested ID. Load fixup `0049f18a` traverses it before the train list and dispatches wagon/engine fixups for native kinds 0x4000d/0x4000e. Pass217 verifies 12 functions, 3,362 instructions and 13,153 bytes against disk and live memory, with no mismatches or read errors. Some functions overlap prior exports; these are not unique coverage totals.

`004a041e` is a class-method dispatcher, not an allocator. Given object-table index ECX and method number EDX, it resolves the object, reads its first word as a class-table index, resolves that class object through the same table, loads slot `[class+0x64+method*4]`, then invokes `[class+0x1064+slot*4]` with the object as ECX. The list consumers request method0x14. This corrects the allocator wording in the older load-identity report.

The observed class-method targets `005f15ac` and `0063465b` return constants 0x4000e and 0x4000d respectively. Native save/load dispatch connects these to engine and wagon paths. Pass218 verifies four exported functions, 327 instructions and 1,038 bytes with no disk/live differences or read errors. The probe resolves the method metadata and checks the complete 16-byte constant-return function before assigning either known kind. It never calls a native method. Unknown targets remain unknown and are not decoded using vehicle offsets.

`read_physical_registry.py` captures the list independently, then compares it with connected train-chain membership. `physical-registry-paused-01` observes paused clock73904.5 at both endpoints, 45 objects: four engines and 41 wagons, covering the 23-car player and 22-car AI. All root/node/table/class rereads are stable, all 45 reciprocal list checks pass, and all 45 body-owner checks pass. The independent list and train chains have identical vehicle membership: zero additional physical vehicles, zero missing connected vehicles. This is a positive enumeration and membership check, not positive detached/static-vehicle coverage.

The native object ID at vehicle+0x50 is distinct from its address and from train+0x10 ID. It is used by the traced lookup and save references. Existing save/reload evidence preserves 23 player vehicle IDs while changing all addresses, but global uniqueness, reuse policy and persistence across unrelated sessions remain unproven. A raw native kind is a type discriminator, not a locomotive control type or proof that a particular system is actively simulated.

Three candidates are added: physical-object registry, vehicle native kind, and vehicle native object ID. Existing car identity/ownership/body fields gain this alternative enumeration evidence without duplicating their values. A physical-list member outside connected train chains would be a set difference, not automatically a detached wagon: lifecycle transitions or unknown ownership could produce it. Static consists may occupy other paths or be unphysicalized. Further producer/removal tracing and a positive fixture are required before claiming completeness for detached or static vehicles.
